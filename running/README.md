# Running

Private, single-user marathon-training PWA (front end only). The backend is the
`running-coach` Firebase project (Cloud Functions + Firestore) in `Bobby-zs-lo/Running-with-Claude`
(design spec: `docs/superpowers/specs/2026-10-04-running-coach-design.md`, sections 4.6 and 5).

**Hidden:** not linked from the site, `noindex,nofollow`, `Disallow: /running/` in
`robots.txt`. The page is an empty shell; all data comes from the API after Google sign-in.

## Sign-in (Firebase Auth)

- **Google sign-in only**: `signInWithPopup` with `GoogleAuthProvider`, session kept with
  `browserLocalPersistence`, so you sign in once per phone. The login screen is a single
  "Sign in with Google" button. The backend decides who the owner is; any other Google
  account gets `403 {"error":"not the owner"}`, and the app shows "This account isn’t allowed"
  and signs out.
- **SDK**: Firebase JS SDK **12.3.0** as ES modules straight from
  `https://www.gstatic.com/firebasejs/12.3.0/firebase-{app,auth}.js` (no npm, no bundler).
  `js/auth.js` loads them with dynamic `import()` on first use. To upgrade, change
  `FIREBASE_SDK` in `js/auth.js`.
- **API calls**: every request sends `Authorization: Bearer <Firebase ID token>`
  (`getIdToken()`, the SDK refreshes it before it expires). `401` signs out of Firebase, clears
  the offline API copies and opens `#/login`.
- **Router guard**: `app.js` shows "Checking sign-in…" until Firebase has restored the saved
  session, then picks `#/login` or the requested view. Sign-in/out (also from another tab)
  moves between the two automatically.
- **Settings › Account**: "Sign out" signs out of Firebase on this phone and clears the API
  cache (no server call). "Sign out everywhere" first calls `POST /api/logout-all` (the
  backend revokes the refresh tokens), then signs out here.
- **Setup**: fill `FIREBASE_CONFIG` (`apiKey`, `authDomain`, `projectId`, `appId`, all public)
  in `js/config.js`, enable the Google provider in Firebase Auth, and add the site's domain
  (`bobbylo.dk`) under Auth › Settings › Authorised domains.
- **Tests**: if `globalThis.__RUNNING_TEST_AUTH__` exists when `auth.js` loads, it is used
  instead of Firebase (same methods: `initAuth`, `onUser`, `signIn`, `signOut`, `getIdToken`,
  `currentUser`) and the SDK is never imported. The smoke test injects one with
  `page.addInitScript`.

## Service worker and `API_BASE`

`sw.js` is registered with `{ type: 'module' }` (Chrome and Android Chrome 91+) and does
`import { API_BASE } from './js/config.js'`, so the API URL lives in one file. Chrome
also checks imported modules for updates, so editing `config.js` updates the SW.
`API_BASE` may include a path (the Cloud Function's `/api`); request paths such as
`/api/state` are appended to it, and the SW strips that prefix before matching the routes it
keeps offline copies of.

The SW never intercepts the Firebase SDK (`www.gstatic.com`) or Google sign-in/token hosts
(`*.googleapis.com`, `accounts.google.com`, `*.firebaseapp.com`): they go straight to the
network. Notification action buttons still `POST /api/notification-action` from the SW with the
single-use action token from the push payload; no ID token is involved.

## Desk layout

At 1100 px and wider `js/layout.js` sets `<html data-layout="desk">`: the tab bar becomes a left
rail, the phone views sit in a 760 px reading column, and the desk-only **Overview** joins the
rail. **Routes** is in both: the sixth tab of the phone bar, where Strava and Garmin export only
download (their web importers are no use on a phone) and *Share GPX…* appears when the browser can
share files. Every desk rule is scoped to that attribute; the Overview tab is in the phone DOM but
hidden, and an Overview link opened on a phone still renders, in one column. The layout follows
the window live, across the breakpoint.

A bare URL, an unknown route and a fresh sign-in all land on the layout's home: Overview on a
desk, Today on a phone. That is why the manifest's `start_url` is a bare `./` (its `id` stays
`/running/`, the name an installed app is known by).

- **Overview** is cross-filtered like a BI report. The range, the sport and a picked week live in
  the hash, so a view can be bookmarked; a filter click rewrites the hash with `replaceState` and
  repaints the tiles in place. Its responses are kept for the visit only. The heatmap frames the
  densest cluster of starts (a trip abroad doesn't zoom it out to the world), and Heatmap and Last
  activity have *Enlarge*, a modal with a large map.
- **Customise** (Overview header) turns every card, each KPI included, into a tile with a drag
  handle, S/M/L/XL widths and a hide button; hidden cards wait in a tray. Pointer or keyboard drag
  (Space picks up, arrows move, announced). *Done* saves the layout to `settings.dashboard`
  (`{ version: 1, tiles: [{ id, span, hidden }] }`, or `null` for the default), so it follows the
  owner to any laptop. The tile catalogue and the pure layout functions are in `overview-model.js`;
  `overview-layout.js` is customise mode's page code and `css/overview-edit.css` its styles.
- **Routes** plans a route three ways, and hands the one on screen on as a GPX file, a Google Maps
  link, a Strava or Garmin import, or (a ride) a Cake, Coffee & Cadence plan:
  - **Auto** asks the backend for three round trips of a set length (`POST /api/routes/generate`;
    the server calls OpenRouteService).
  - **Draw**: each click on the map adds a point, and the route follows paths and roads between them
    (`POST /api/routes/plan`). It starts from the Start (home, if set); *Back to start* closes the
    loop (on by default for runs).
  - **Edit**: any route with points can be reshaped, like CCC's shaping points. *Edit this route*
    turns an Auto variant into its start plus six points spread along it, re-planned once. Drag a
    point, or grab the line to pull a new point out of it; click a point to remove it (not the
    start; two stay). With a finger, which cannot pull the line, a tap on the line adds a point
    there. From the keyboard, Tab to a point: arrows move it 20 m (Shift: 100 m; presses close
    together are one undo step and one plan), Delete removes it. Each edit re-plans with one request in flight at most; the old line stays faded
    until the new one arrives, and a point too far from any path is put back. Undo and Redo
    (Ctrl+Z, Ctrl+Shift+Z) keep 30 steps and step back to a planned state without a new request.
    A live readout on the map shows the distance against the target and the climb.

## Linking recorded sessions to a workout

The backend matches a Strava activity to the day's planned workout by itself; which sessions
count is the owner's to change. On `#/workout/<id>`, *Change* under "What you actually did" (or
*Link a recorded session* when nothing is linked yet) opens an editor in that card: one checkbox
per session recorded that day, Strava first, then Health Connect, each with its distance, duration
and start time. One, several (a warm-up and the session count together) or none can be ticked. A
Health Connect session that is a copy of a Strava activity is listed but cannot be ticked, and is
never counted or sent, even if it still carries a link from before Strava had the session; a
session that counts for another workout of the day says so, and ticking it moves it. *Save* sends
the complete set, `PUT /api/workouts/:id/links { activityIds: string[], healthIds: string[] }`
(at most ten of each), then reads the week and the plan again: the status follows the links (done
at 80 % of the plan, else partial, planned with nothing linked) unless it was set by hand. Links
are same-day only; a session run on another day is handled by moving the workout first.

`#/workout/<id>?link=1` opens the editor straight away. Today links there from each card (*Change*
beside what counts, or *Link a recorded session →* when nothing counts but a session of the
workout's own sport was recorded, so the ride to work does not prompt on a planned run), and so
does the Activity page (*Change*, or *Link it to …* for each session planned that day). Today, Week
and the session page show a linked Health Connect session as a row beside the Strava ones.

## Maps

Leaflet 1.9.4 loads from cdnjs with subresource integrity, only once a map is about to show, so a
page without one never pays for it and an offline phone loses only the map. Every line is drawn on
one canvas renderer: a heatmap of every route would otherwise be tens of thousands of SVG nodes.

The tiles are OpenStreetMap's own. CARTO's raster tiles were the first choice, but they now need
an API key: on 6 October 2026 every tile came back reading "API KEY REQUIRED". OSM's tile policy
accepts a small private app if each request carries a Referer and the credit is shown.
`index.html` sends no Referer (`<meta name="referrer" content="no-referrer">`), which OSM answers
with an "Access blocked" tile, so the tile layer alone sends the origin
(`referrerPolicy: 'origin'`): it names the site, never the page. One tile set serves both colour
schemes; `css/map.css` themes it with a filter.

## Tests

```sh
bash running/tests/run-all.sh            # unit tests (node 22)
PLAYWRIGHT_NODE_MODULES=/path/to/node_modules SHOTS_DIR=/tmp/shots \
  bash running/tests/run-all.sh --smoke  # + browser smoke test, mocked API
```

The smoke test serves the repo root, fakes Firebase Auth (see above), answers the API from the
shared mock (`tests/mock-api.mjs`; a planned route is made up in `tests/mock-plan.mjs`, and a point
dropped in the Øresund east of the fictional home answers 502 as OpenRouteService would; the links
endpoint, with the backend's rules and messages, is `tests/mock-links.mjs`, and what it changes
lasts as long as that mock) on the
invented data in `tests/fixtures/` (rebuild with
`node running/tests/fixtures/build-fixtures.mjs`), and saves screenshots. Playwright is not a
dependency of this repo. Install it somewhere else, and point `CHROMIUM_PATH` at its Chromium
unless that is at `/opt/pw-browsers/chromium`. On Windows, for instance:

```sh
CHROMIUM_PATH="$LOCALAPPDATA/ms-playwright/chromium-<build>/chrome-win64/chrome.exe" \
PLAYWRIGHT_NODE_MODULES=/path/to/node_modules SHOTS_DIR=/tmp/shots \
  node running/tests/smoke.playwright.mjs
```

Set `REAL_FONTS=1` to load Google Fonts for screenshots.

## Preview server

```sh
node running/tests/preview-server.mjs [--port 5173] [--home]
```

Runs the app at `http://127.0.0.1:5173/running/` on synthetic data only: `js/config.js` is served
with `API_BASE` pointing at the server's own `/mock-api` (the smoke test's mock), a fake signed-in
user stands in for Firebase, and service-worker registration is a no-op, so nothing is cached.
`--home` gives the mock settings a home location, so Routes has a start. Edit the files and reload.

Why: the app shows Strava data, and Strava's API policy forbids that data reaching an AI. A Claude
session working on the app runs it here, and never against the live API.

## Routes

Hash routes, parsed by `js/router.js`; path segments after the view name arrive as `ctx.rest`.

`#/login` · `#/today` · `#/week?date=` · `#/plan` · `#/health` · `#/reviews` · `#/settings` ·
`#/workout/<workoutId>?link=` (`1` opens the editor of what counts) · `#/activity/<activityId>` · `#/overview?p=&s=&w=` (range `4w`, `12w`,
`season`, `1y` or `all`; sport `run`, `ride` or `all`; a picked week's Monday) ·
`#/routes?km=&profile=&from=&mode=` (distance, `trail` or `ride`, the planned run it is for, `draw`)

Adding a view means three registrations: `VIEWS` and `TITLES` in `js/app.js`, `ROUTES` in
`js/router.js`, and the `SHELL` precache list in `sw.js`. Then bump `APP_VERSION`.

## Setup status

Live since 5 October 2026 and fully set up. `js/config.js` holds the real `API_BASE` and
`FIREBASE_CONFIG`; both Firebase values are public identifiers, not secrets.

**`APP_VERSION` in `js/config.js` must be bumped on every change.** It names the service-worker
shell cache, and without a bump phones keep serving the old files. `config.js` and
`manifest.webmanifest` are deliberately network-first in `sw.js`: one carries the API URL and the
other the app's identity, and a stale cached copy of either cannot be recovered from inside the page.

The backend, the decisions behind the plan, and the traps worth knowing are documented in
[`Running-with-Claude/HANDOFF.md`](https://github.com/Bobby-zs-lo/Running-with-Claude/blob/main/HANDOFF.md);
open items are in [`STATUS.md`](https://github.com/Bobby-zs-lo/Running-with-Claude/blob/main/STATUS.md).
